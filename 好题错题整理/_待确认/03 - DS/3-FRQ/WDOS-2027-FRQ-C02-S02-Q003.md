## DeepSeek V4 Flash Max 解析
**答案**：
（I）该系统应采用时间片轮转调度算法（$\mathrm{RR}$），即基于时间片的抢占式调度。

（II）按图中常见编号（五状态模型）对应如下：

| 变化 | 原因 |
| --- | --- |
| $1$：创建态（新建态） $\rightarrow$ 就绪态 | 进程创建完成，$\mathrm{PCB}$ 初始化好，进入就绪队列等待调度。 |
| $2$：就绪态 $\rightarrow$ 运行态 | 调度程序从就绪队列中选中该进程，分配 $\mathrm{CPU}$，发生上下文切换。 |
| $3$：运行态 $\rightarrow$ 阻塞态 | 进程请求 I/O、等待某事件或申请资源未满足，主动让出 $\mathrm{CPU}$。 |
| $4$：运行态 $\rightarrow$ 就绪态 | 时间片用完，进程被剥夺 $\mathrm{CPU}$，回到就绪队列队尾。 |
| $5$：阻塞态 $\rightarrow$ 就绪态 | I/O 完成或等待的事件发生，进程被唤醒，进入就绪队列。 |
| $6$：运行态 $\rightarrow$ 终止态 | 进程正常结束，或发生异常/被终止，系统回收 $\mathrm{PCB}$ 与资源。 |

**解题切入点**：
看到“分时系统”优先想到时间片轮转；再看到图中存在“运行态 $\rightarrow$ 就绪态”这条边，且原因应该是“时间片到”，就能锁定 $\mathrm{RR}$。状态转换图本质上就是一张有向图，和算法竞赛里的状态机、$\mathrm{BFS/DFS}$ 状态搜索一样：每个状态是结点，每条编号边对应一个“触发事件”。阻塞/唤醒可看成资源等待与释放：进程等不到资源就进入阻塞，事件完成后被放回就绪队列，类似图论匹配中“进程等待资源点可用”的过程。

**推演**：
设就绪队列为 $Q$，时间片为 $q$。时间片轮转的调度循环是：

$$
Q.\text{pop}() \to \text{运行态}, \quad \text{运行 } q \text{ 后} \to Q.\text{push\_back}(\text{当前进程})
$$

- 创建态 $\rightarrow$ 就绪态：新进程创建完成，入就绪队列，等待被调度。
- 就绪态 $\rightarrow$ 运行态：调度器从队首取出进程，分配 $\mathrm{CPU}$。
- 运行态 $\rightarrow$ 阻塞态：进程因 I/O、锁、信号量等待等事件主动睡眠。
- 运行态 $\rightarrow$ 就绪态：时间片耗尽，时钟中断触发抢占，进程排到队尾。
- 阻塞态 $\rightarrow$ 就绪态：等待的事件发生，进程被唤醒，入就绪队列。
- 运行态 $\rightarrow$ 终止态：执行完毕或异常退出，状态机走到终点。

关键不变量：合法转移只有“就绪 $\leftrightarrow$ 运行、运行 $\rightarrow$ 阻塞、阻塞 $\rightarrow$ 就绪、运行 $\rightarrow$ 终止”；不存在“阻塞 $\rightarrow$ 运行”直接转移，也不存在“就绪 $\rightarrow$ 阻塞”直接转移。

**易错点**：
- 不要把“运行态 $\rightarrow$ 阻塞态”写成“被剥夺 $\mathrm{CPU}$”；被剥夺 $\mathrm{CPU}$ 应回到就绪态。
- 不要把“阻塞态 $\rightarrow$ 就绪态”写成“阻塞态 $\rightarrow$ 运行态”；唤醒后必须排队等调度。
- “就绪态 $\rightarrow$ 运行态”不是自动发生的，必须由调度程序选择。
- 策略只答“抢占式调度”不够准确，分时系统通常标准答案是时间片轮转（$\mathrm{RR}$）。
- 创建态和终止态容易被忽略；创建不等于被调度，终止要回收资源，而不是回到就绪队列。

**命题规律**：
常以进程状态转换图考查“调度策略 + 状态转换原因”，本质是显式状态机与事件驱动。可以进一步结合时间片大小、就绪队列排队顺序、平均周转时间/等待时间出计算题。做题时用算法竞赛的状态搜索思维：先记合法状态集合，再对每条边找触发事件；看到“分时系统”就优先匹配时间片轮转。
