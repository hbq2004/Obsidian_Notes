# MCQ 第 16 题

![[_Attachments/题目识别/WDOS-2027-MCQ/WDOS-2027-MCQ-C02-S02-Q016_题目.png|题目]]

每个作业只能建立一个进程,为了照顾短作业用户,应采用 ( ) ; 为了照顾紧急作业用户,应采用 ( ) ; 为了能实现人机交互，应采用 ( ) ；而能使短作业、长作业和交互作业用户都满意，应采用 ( ).
(A) $FCFS$ 调度算法
(B) 短作业优先调度算法
(C) 时间片轮转调度算法
(D) 多级反馈队列调度算法
(E) 剥夺式优先级调度算法

## DeepSeek V4 Flash Max 解析
**答案**：
依次选：$B,\ E,\ C,\ D$。

| 用户需求 | 调度算法 |
|---|---|
| 照顾短作业用户 | (B) 短作业优先调度算法 |
| 照顾紧急作业用户 | (E) 剥夺式优先级调度算法 |
| 实现人机交互 | (C) 时间片轮转调度算法 |
| 短、长、交互作业都满意 | (D) 多级反馈队列调度算法 |

**解题切入点**：
题目本质是“调度目标 → 调度算法”的匹配。由于每个作业只能建立一个进程，可把作业和进程都看作一个“任务实体”，不必区分作业调度与进程调度。

从算法竞赛视角看：短作业优先类似“按处理时间升序排序”的贪心；剥夺式优先级类似“每次取优先级最高者”的优先队列；时间片轮转类似“多路请求轮询”；多级反馈队列则像“分层决策 / 动态调参”，不同任务走不同队列，兼顾多种目标。

**推演**：
1. 照顾短作业用户：  
   短作业用户希望自己的周转时间短。若作业 $i$ 的服务时间为 $\tau_i$，等待时间为 $W_i$，则周转时间
   $$
   T_i = W_i + \tau_i,\quad \overline{T}=\frac{1}{n}\sum_{i=1}^{n} T_i
   $$
   由于 $\tau_i$ 固定，要减小平均周转时间就要减小 $\sum W_i$。短作业优先每次选 $\tau_i$ 最小的作业执行，等价于按服务时间从小到大贪心，能最小化平均等待时间，因此选 $B$。

2. 照顾紧急作业用户：  
   紧急作业不是“短作业”，而是“急需处理”的任务。剥夺式优先级调度会给紧急作业赋高优先级，一旦高优先级任务到达，立即抢占当前运行的进程。这相当于用一个大根堆维护就绪任务，每次取优先级最高的任务执行，因此选 $E$。非剥夺式优先级无法做到“紧急时立刻抢 CPU”。

3. 实现人机交互：  
   交互式用户要求响应时间短且有界。时间片轮转将 CPU 时间切成固定时间片 $q$，按就绪队列循环分配；若系统中有 $m$ 个就绪进程，一个进程两次获得 CPU 的间隔约为 $(m-1)q$，响应时间可预测。这正适合分时交互系统，因此选 $C$。

4. 短作业、长作业、交互作业都满意：  
   多级反馈队列设置多个优先级队列，高优先级队列时间片短，低优先级队列时间片长。新进程先进入最高优先级队列，按时间片轮转调度；若用完时间片还未完成，则降入下一级队列；交互型进程常因 I/O 主动让出 CPU，可留在高优先级队列。短作业在高优先级队列很快完成，交互作业能及时响应，长作业在低优先级队列用较长时间片慢慢运行。因此选 $D$。

**易错点**：
- 不要把“短作业”和“紧急作业”混为一谈：短作业优先只看运行时间，不关心紧急程度；紧急作业需要优先级调度，并且要能剥夺。
- 优先级调度不一定是剥夺式。题目特别强调“剥夺式”，就是要求高优先级任务到达后能立即抢占 CPU。
- 第三空容易误选多级反馈队列：多级反馈队列确实也支持交互，但直接实现“人机交互 / 分时系统”的经典算法是时间片轮转；多级反馈队列是第四空的综合方案。
- 第四空不能选短作业优先：短作业优先会饿死长作业；多级反馈队列通过降级和增大时间片对长作业兜底，才能“都满意”。
- FCFS 公平但不对任何特定目标优化，因此本题四个空都不选它。

**命题规律**：
408 常以“某一类用户需求”为题干，要求匹配调度算法。复习时按三个维度记忆即可：目标函数、实现机制、代价或饥饿风险。

- 短作业优先：优化平均等待时间，但长作业可能饥饿。
- 剥夺式优先级：处理紧急任务，但低优先级可能饥饿。
- 时间片轮转：保证交互响应时间，但上下文切换开销较大。
- 多级反馈队列：综合短作业、长作业与交互需求，是“折中 / 自适应”方案。

这种题目本质上像构造题：先明确要优化的指标，再选择对应算法；不要死记答案，而要问自己“这个算法到底在优化什么”。
