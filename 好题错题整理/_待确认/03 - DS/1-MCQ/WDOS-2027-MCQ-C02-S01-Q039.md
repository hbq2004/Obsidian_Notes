# MCQ 第 39 题

![[_Attachments/题目识别/WDOS-2027-MCQ/WDOS-2027-MCQ-C02-S01-Q039_题目.png|题目]]

39. 在以下描述中，( \\_ ) 并不是多线程系统的特长。

(A) 利用线程并行地执行矩阵乘法运算

(B) $Web$ 服务器利用线程响应 $HTTP$ 请求

(C) 键盘驱动程序为每个正在运行的应用配备一个线程,用以响应该应用的键盘输入

(D) 基于 $GUI$ 的调试程序用不同的线程分别处理用户输入、计算和跟踪等操作

## DeepSeek V4 Flash Max 解析
**答案**：  
$\mathrm{C}$

**解题切入点**：  
本题要求判断哪项不属于多线程系统的优势，考察多线程典型应用场景的界定。多线程系统擅长处理可并行化计算、提升 I/O 响应速度、分离不同关注点（如 GUI 与后台任务），但若任务本质是串行事件、中断驱动且全局共享资源，强行引入线程反而增加开销与复杂度。可类比算法竞赛中，并行化运算适合用分治（如 FFT 的蝶形变换），而构造题则需集中处理逻辑，若强行用多路分支反而低效。

**推演**：  
- 选项 A：矩阵乘法可分解为独立子任务，利用多线程并行执行加速，符合多线程特长（类似分治中并行归并）。  
- 选项 B：Web 服务器需同时处理大量 HTTP 请求，每个请求独立，用线程池实现并发响应，提高吞吐量（类似网络流中多路复用）。  
- 选项 C：键盘输入本质是全局中断事件，由硬件产生后经操作系统统一分发，若为每个应用分配一个线程持续监听键盘，则大部分线程会因等待输入而阻塞，频繁切换浪费资源；且键盘输入需要顺序处理，多个线程反而引入竞态（类似图论中单源最短路径，多源发散反而冗余）。  
- 选项 D：GUI 调试程序将用户输入、计算、跟踪分离为不同线程，避免界面卡顿，利用线程隔离不同任务（类似状态机中不同状态用独立 DFS 分支处理）。  

因此，选项 C 不是多线程系统的特长，响应键盘输入更适合中断驱动而非多线程轮询。

**易错点**：  
- 误认为“每个应用一个线程”能提高响应速度，但线程的创建、切换、同步开销会远大于收益，且键盘输入是串行事件，多线程无法并行处理。  
- 混淆“多线程”与“多进程”或“中断处理”，键盘驱动程序常用中断下半部（tasklet）而非用户态线程。  
- 将 Web 服务器与键盘驱动等同看待，忽略 Web 请求是独立且可并行，而键盘输入是全局共享资源。

**命题规律**：  
- 常以“特长/优势/不适用的场景”形式考查多线程与进程、中断的适用边界。  
- 选项设计多包含典型并行计算（A）、I/O 并发（B）、GUI 分离（D）以及一个反直觉的“串行资源”场景（C）。  
- 备考时需类比算法中的“并行化适用条件”：仅当任务可分解为无依赖子问题（如分治）时才适合多线程；若任务本质是序列依赖或全局互斥（如 DAG 中的关键路径），则多线程无益。
