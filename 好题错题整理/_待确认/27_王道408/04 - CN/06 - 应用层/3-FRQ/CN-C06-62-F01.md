# 综合题 第 1 题

![[_Attachments/题目识别/27_王道408-题目/CN-C06-62-F01_题目.png|题目]]

1. DNS 使用 UDP 而非 TCP,若一个 DNS 分组丢失,没有自动恢复,那么这会引起问题吗?若会,应该如何解决?

---

## 答案

![[_Attachments/题目识别/27_王道408-答案/CN-C06-62-F01_答案.png|答案]]


## DeepSeek V4 Flash Max 解析

**答案**：会。UDP 本身只提供“尽力而为”的交付，分组丢失后不会像 TCP 那样自动重传；解决办法是把可靠性上移到应用层：DNS 客户端设置超时定时器并重发查询，必要时换 DNS 服务器或改用 TCP。一句话：问题存在，但可通过 DNS 应用层的超时重传解决。

**解题切入点**：拿到题先抓“丢包后由谁恢复”。TCP 的可靠由传输层负责，UDP 不负责；若应用需要可靠，只能由应用层自己实现，或者改用 TCP。这就像算法竞赛中一个 API 可能超时/报错，你不会指望库自动重试，而是自己封装一个带超时重试的辅助函数；协议分层就是分治，每一层只做自己的子任务，传输层不提供可靠时，应用层就要自己补上这个子任务。

**推演**：

1. DNS 正常查询过程：客户端向 DNS 服务器发送一个 UDP 查询 $Q$，服务器返回响应 $R$。  
2. 若 $Q$ 丢失：服务器根本收不到查询，不会返回 $R$。  
3. 若 $R$ 丢失：服务器已处理，但客户端收不到响应。  

以上两种情况在客户端看来都是“超时未收到响应”。UDP 没有序号、确认和重传机制，运输层不会自动恢复。

解决办法：客户端设置重传超时时间 $T$，超时后重新发送 DNS 查询；如果连续失败，可以指数退避，重试若干次后换下一个 DNS 服务器。由于 DNS 查询通常是幂等的，重复发送不会破坏服务器状态；DNS 报文中的事务 ID（$\text{ID}$）用于匹配响应和请求，重复或迟到的响应可以被识别并丢弃。

特殊情况下，若 UDP 响应因超过 512 字节而被截断，或者进行区域传送（AXFR/IXFR）时必须改用 TCP，因为 TCP 提供可靠的字节流传输。但正常域名解析仍以 UDP 为主，以降低时延和连接开销。

**易错点**：

- 误认为“UDP 丢包就无解”。实际上 UDP 不自动重传，但应用层可以重传。  
- 误认为“DNS 应全部改用 TCP”。TCP 会增加握手时延和连接状态，只适合大响应或区域传送；日常查询用 UDP 更高效。  
- 误认为“服务器超时后重发响应”。DNS 服务器通常无状态，不知道客户端是否收到响应，重传应由客户端发起。  
- 忽略重传的匹配与去重。必须使用事务 ID 和超时策略，否则可能把旧的迟到响应误认为当前响应。

**命题规律**：

考点是“应用层协议与传输层服务的匹配关系”，常以选择题或简答题考查：DNS 为什么用 UDP？何时用 TCP？丢包后如何保证可靠？常见变式是把 DHCP、TFTP 等同样基于 UDP 的协议放在一起，问它们如何解决可靠性。复习时不要只背端口号，要针对每个应用层协议问三个问题：用 TCP 还是 UDP？为什么？需要可靠时由谁负责？
