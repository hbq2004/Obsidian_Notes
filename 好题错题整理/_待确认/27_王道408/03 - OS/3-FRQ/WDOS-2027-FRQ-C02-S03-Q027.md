# FRQ 第 27 题

![[_Attachments/题目识别/WDOS-2027-FRQ/WDOS-2027-FRQ-C02-S03-Q027_题目.png|题目]]

现要求学生使用 $swap$ 指令和布尔型变量 $lock$ 实现临界区互斥。$lock$ 为线程间共享的变量,当 $lock$ 的值为 $TRUE$ 时线程不能进入临界区,为 $FALSE$ 时线程能够进入临界区。某同学编写的实现临界区互斥的伪代码如图 $a$ 所示。请回答下列问题.

## DeepSeek V4 Flash Max 解析
**答案**：  
图 a 所示代码（典型错误：将临时变量 `key` 设为全局而非线程局部）**不能实现临界区互斥**，它可能使多个线程同时进入临界区，违反互斥条件。改进方法：将 `key` 定义为每个线程的局部变量，并在 `do-while` 循环前初始化为 `TRUE`；退出临界区时将 `lock` 置为 `FALSE`。改进后的算法满足互斥和空闲让进，但不满足有限等待（可能出现饥饿）。

**解题切入点**：  
从临界区互斥三条件（互斥、空闲让进、有限等待）出发，分析 `swap` 指令的原子性及变量作用域。`swap` 原子交换能保证锁获取的互斥性，但 **`key` 必须为线程私有**，否则隔离性被破坏。这类似算法竞赛中用 `atomic_exchange` 实现自旋锁：每个线程应有独立的“标签”变量，若标签共享则相当于多线程 DFS 共用同一访问数组，状态相互覆盖。

**推演**：  
以全局 `key` 版本（`lock=FALSE`、`key=TRUE`）演示互斥失败：  
1. 线程 A 执行 `swap(&lock,&key)`：`lock=TRUE, key=FALSE` → A 因 `key=FALSE` 进入临界区。  
2. 线程 B 执行 `swap(&lock,&key)`：`lock=TRUE, key=FALSE` → 交换后 `lock=FALSE, key=TRUE`，B 因 `key=TRUE` 循环等待，但已误将 `lock` 改为 `FALSE`。  
3. 线程 C 执行 `swap(&lock,&key)`：`lock=FALSE, key=TRUE` → 交换后 `lock=TRUE, key=FALSE`，C 进入临界区，与 A **同时存在**，互斥失败。  
若 `key` 为局部变量，每个线程独立交换，则不会出现锁状态被意外修改的情况：每个线程用私有 `key_local` 与 `lock` 交换，只有原 `lock=FALSE` 时 `key_local` 变为 `FALSE` 才进入，从而保证互斥。

**易错点**：  
1. **全局临时变量**：将交换用的 `key` 设为全局，导致多线程 `swap` 相互干扰锁状态。  
2. **循环结构失误**：使用 `while(lock)` 而非 `do-while`，可能使多个线程同时检测 `lock=FALSE` 而跳过进入区，违反互斥。  
3. **初值错误**：如 `lock` 初始为 `TRUE`，则第一个线程无法进入（不满足空闲让进）；`key` 初值不为 `TRUE` 可能导致自旋逻辑混乱。  
4. **退出区遗漏**：未在退出临界区时将 `lock` 置 `FALSE`，导致后续线程死锁。  
5. **`swap` 语义误解**：将常量直接作为第二参数（如 `swap(&lock,TRUE)`），不符合原子交换需要变量的要求。  
这些陷阱可类比竞赛中用 `CAS` 实现锁时误用共享 `expected` 值或循环条件反置。

**命题规律**：  
408 常以 `Swap`、`TSL`、`XCHG` 等硬件指令为背景考查互斥算法分析，重点考察变量作用域（局部/全局）、初始值设置、循环结构及退出区操作，并要求判断互斥、空闲让进、有限等待三个条件。常见结论：自旋锁通常满足互斥和空闲让进，但不满足有限等待（饥饿）。解题时建议用时间序列枚举验证互斥性，并类比竞赛中原子操作锁的通病（如 ABA 问题、错误共享变量），避免相同错误。
