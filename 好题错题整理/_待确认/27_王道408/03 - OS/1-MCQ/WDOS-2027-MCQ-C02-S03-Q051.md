# MCQ 第 51 题

![[_Attachments/题目识别/WDOS-2027-MCQ/WDOS-2027-MCQ-C02-S03-Q051_题目.png|题目]]

使用 $TSL(TestandSetLock)$ 指令实现进程互斥的伪代码如下所示.

```
do{
    ...
    while(TSL(&lock));
    critical section;
    lock=FALSE;
    ...
} while(TRUE);
```

下列与该实现机制相关的叙述中,正确的是（ ）
(A) 退出临界区的进程负责唤醒阻塞态进程
(B) 等待进入临界区的进程不会主动放弃 $CPU$
(C) 上述伪代码满足“让权等待”的同步准则
(D) $while(TSL(amp;lock))$ 语句应在关中断状态下执行

## DeepSeek V4 Flash Max 解析
**答案**：B

**解题切入点**：
TSL 是一条“读-改-写”的硬件原子指令，可理解为
$$
\operatorname{TSL}(lock): old \leftarrow lock;\ lock \leftarrow TRUE;\ return\ old
$$
当 $lock$ 为 $FALSE$ 时，第一个执行 $TSL$ 的进程得到 $FALSE$ 并进入临界区；之后其它进程执行 $TSL$ 都得到 $TRUE$，只能在循环里自旋。因此本题本质是“忙等/自旋锁”，不是“阻塞/睡眠等待”。算法竞赛里可以类比为 `while (!ready);`：条件不满足时不把任务挂起，而是占着当前线程空转；正确的事件驱动写法应把任务放入等待队列，条件满足后再唤醒。这样一看，“让权等待”显然不满足。

**推演**：
- A 错误：退出临界区只做 $lock=FALSE$，不会唤醒任何进程；自旋等待的进程本来就没有进入阻塞态，不存在“阻塞态进程”需要唤醒。
- B 正确：等待进程一直在循环中反复执行 $TSL$，不会主动调用阻塞/睡眠/让出 CPU 的原语；它占着 CPU 空转，最多只能被调度器被动抢占。
- C 错误：让权等待要求进程在无法进入临界区时主动释放 CPU，自旋锁没有做到。
- D 错误：$TSL$ 指令已经由硬件保证原子性，不需要再关中断；如果对整个 `while(TSL(&lock));` 关中断，拿不到锁的进程会一直空转，甚至可能屏蔽时钟中断，导致系统无法正常调度。

**易错点**：
- 把“等待”一律理解为“让权等待”。本题中 `while` 自旋是忙等，不释放 CPU。
- 把 $lock=FALSE$ 当成唤醒。自旋锁没有等待队列，释放锁只是让其它自旋进程有机会再次抢到锁；唤醒是阻塞机制中的操作。
- 认为 TSL 需要关中断。$TSL$ 是原子指令，不是靠关中断实现；关中断只是另一种互斥手段。
- 把“不会主动放弃 CPU”理解成“永远不会被切换”。如果系统是抢占式调度，时间片到了仍可能被剥夺 CPU，但这属于被动切换，不是主动让权。

**命题规律**：
408 经常用一个简单互斥代码把“硬件指令、忙等、让权等待、阻塞唤醒”串起来考。看到 `while(TSL(&lock))` 或 `Swap` 指令，应先打上“自旋锁”标签，再检查选项是否涉及“阻塞唤醒”“让权等待”“关中断”。复习时可把互斥实现按层次分类：软件算法、硬件指令、信号量/管程；每种都问一遍：等待时进程状态是什么、是否释放 CPU、谁负责唤醒。这与竞赛中“轮询等待”和“队列唤醒/事件驱动”的区别类似：轮询写起来简单但空转浪费资源，真正的并发调度要靠等待队列和唤醒条件。
