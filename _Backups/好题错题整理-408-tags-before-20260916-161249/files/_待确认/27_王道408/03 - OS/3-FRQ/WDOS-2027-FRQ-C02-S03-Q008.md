# FRQ 第 8 题

![[_Attachments/题目识别/WDOS-2027-FRQ/WDOS-2027-FRQ-C02-S03-Q008_题目.png|题目]]

8. 假设有两个线程(编号为 0 和 1)需要去访问同一个共享资源,为避免竞争状态的问题,我们必须实现一种互斥机制，使得在任何时候只能有一个线程访问这个资源。假设有如下一段代码:
```
bool flag[2];                  //flag 数组，初始化为 $FALSE
Enter_Critical_Section(int my_thread_id,int other_thread_id) {
    while(flag$[$other_thread_id$]==TRUE);      //空循环语句
    flag[$my_thread_id$]=TRUE;
$}
Exit_Critical_Section(int my_thread_id,int other_thread_id) {
    flag$[$my_thread_id$]=FALSE;
}
```
当一个线程想要访问临界资源时,就调用上述的这两个函数。例如,线程 0 的代码可能是这样的:
```
$Enter_Critical_Section(0,1)$;
使用这个资源;
$Exit_Critical_Section(0,1)$;
做其他的事情;
```
(1)以上的这种机制能够实现资源互斥访问吗？为什么？
(2)若把 $Enter_Critical_Section()$ 函数中的两条语句互换一下位置，可能发生死锁吗？

## DeepSeek V4 Flash Max 解析
**答案**：

(1) 不能。原因：$\text{Enter\_Critical\_Section}$ 中的 `while` 检查与 $\text{flag}[\text{my\_thread\_id}]=\text{TRUE}$ 是两条独立指令，两者之间可以被调度器打断。可能发生：$T_0$ 检查到 $\text{flag}[1]=\text{FALSE}$，$T_1$ 也检查到 $\text{flag}[0]=\text{FALSE}$，然后 $T_0$、$T_1$ 再分别把自己的 $\text{flag}$ 置为 $\text{TRUE}$。此时两个线程都通过入口函数进入临界区，互斥失败。

(2) 可能。交换后进入协议为：

$$
\text{flag}[\text{my\_thread\_id}]=\text{TRUE};\quad
\text{while}(\text{flag}[\text{other\_thread\_id}] == \text{TRUE});
$$

若 $T_0$、$T_1$ 都先把自己的 $\text{flag}$ 置为 $\text{TRUE}$，再检查对方，则双方都会看到对方的 $\text{flag}$ 为 $\text{TRUE}$，从而陷入空循环等待。没人能进入临界区，也就没人执行 `Exit` 把 $\text{flag}$ 复位，形成循环等待式死锁。

**解题切入点**：

把入口协议看成状态机中的“先检查、后写入”两步。原版等价于：先判断对方不在，再标记自己进入。但这两步不是原子的；在算法竞赛中相当于两个 DFS 进程同时执行 `if (!vis[other]) vis[my]=true;`，由于 `vis` 检查和写入之间可能插入另一个进程的操作，两个搜索进程会同时认为对方还没访问，从而重复进入同一状态。

交换版则变成“先标记自己，再等待对方”，类似于两个进程各自持有一把锁，又都在等对方释放锁。若按有向图表示等待关系，就是 $T_0 \rightarrow T_1$、$T_1 \rightarrow T_0$ 的环；要打破这个环，需要类似 Peterson 算法中的 `turn` 仲裁变量，让其中一方让步。

**推演**：

(1) 原版互斥失效的合法交错：

初始 $\text{flag}[0]=\text{flag}[1]=\text{FALSE}$。

1. $T_0$ 执行 `while (flag[1] == TRUE)`，读到 $\text{FALSE}$，准备退出循环。
2. $T_1$ 执行 `while (flag[0] == TRUE)`，也读到 $\text{FALSE}$，准备退出循环。
3. $T_0$ 执行 $\text{flag}[0]=\text{TRUE}$。
4. $T_1$ 执行 $\text{flag}[1]=\text{TRUE}$。

此后 $T_0$、$T_1$ 都从 `Enter` 返回，同时进入临界区。这说明原版不能保证互斥。

(2) 交换版死锁的合法交错：

1. $T_0$ 执行 $\text{flag}[0]=\text{TRUE}$。
2. $T_1$ 执行 $\text{flag}[1]=\text{TRUE}$。
3. $T_0$ 执行 `while (flag[1] == TRUE)`，读到 $\text{TRUE}$，空转等待。
4. $T_1$ 执行 `while (flag[0] == TRUE)`，读到 $\text{TRUE}$，空转等待。

此后两个线程都在等待对方把 $\text{flag}$ 变为 $\text{FALSE}$，但没人能进入临界区去执行 `Exit`。因此交换后可能发生死锁。

**易错点**：

- 不要把“检查对方不在”和“自己进入临界区”当成一个原子操作；两条指令之间可以被插入其他线程的指令。
- 不要把“互斥失败”和“死锁”混为一谈。原版的问题是可能同时进入临界区；交换版的问题是可能谁也进不去。
- 交换版中“先置自己的 flag 能挡住对方”是对的，但两个线程都先置位时，会互相挡住，形成死锁。互斥性可能满足，但前进/有限等待不满足。
- 如果只考虑“一个线程完整执行完再执行另一个”的串行顺序，会漏掉并发交错；并发系统必须考虑所有合法指令交错，相当于算法题中的最坏情况数据。

**命题规律**：

408 操作系统喜欢考 Peterson 算法及其错误变体，尤其是调换语句顺序、删除 `turn` 变量、把“检查-置位”顺序颠倒等。本题核心是临界区问题的三个条件：互斥、前进、有限等待。原版在互斥性上失败，交换版在前进性上失败。

遇到这类题，先问：每条语句是否原子？是否有检查与修改之间的竞态？等待关系是否会形成环？这与算法竞赛中分析“最坏情况交错”和“状态转移图中是否有环”是同一个思维模式。后续若考修改方案，通常会引导到硬件原子指令 `TestAndSet` 或 Peterson 算法的 `turn` 变量。
