8. HTTP 是一个无状态协议,然而 Web 站点经常希望能够识别用户,这时需要用到( )

(A) Web 缓存

(B) Cookie

(C) 条件 GET

(D) 持久连接

## 答案

![[_Attachments/题目识别/27_王道408-答案/CN-C06-65-M08_答案.png|答案]]


## DeepSeek V4 Flash Max 解析

**答案**：B。理由：HTTP 无状态，但 Web 站点需识别用户，通常借助 Cookie 在客户端保存身份标识并在后续请求中携带，从而“记住”用户。

**解题切入点**：拿到题先抓关键词：“无状态协议”“识别用户”。HTTP 本身不保存用户信息，但应用层需要“会话状态”，这类似于算法竞赛中“无记忆函数”无法维护跨调用状态，必须引入外部数据结构（如哈希表、缓存）来保存状态。这里 Cookie 就是客户端侧的“状态存储/上下文传递”机制。定位考点：HTTP 无状态性与 Cookie 的作用。

**推演**：
HTTP 被设计为无状态（stateless）协议，即每个请求都是独立的，服务器不保留之前的请求信息。若 Web 站点要识别用户（例如保持登录、记录购物车），就必须在请求之外携带用户标识。

常见机制中：
- Web 缓存：缓存的是响应副本（如页面、资源），用于减少传输延迟和网络负载，不能识别用户。
- 条件 GET：配合 `If-Modified-Since` 等首部，使缓存验证资源是否更新，不识别用户。
- 持久连接：通过 `Connection: keep-alive` 复用 TCP 连接，减少连接建立开销，仍不识别用户。
- Cookie：服务器通过 `Set-Cookie` 首部在响应中给客户端一个标识（如 `session_id`），浏览器后续请求自动携带 `Cookie` 首部，服务器据此识别同一用户。

过程可表示为：
1. 用户首次请求：浏览器发出 `GET /index.html`，服务器响应并附加：
   $$
   \text{Set-Cookie: sessionid=abc123; Path=/}
   $$
2. 浏览器保存该 Cookie；
3. 后续请求自动携带：
   $$
   \text{Cookie: sessionid=abc123}
   $$
4. 服务器解析该 Cookie，即识别出同一用户。

因此，“无状态协议 + Cookie”相当于在 HTTP 之上实现了一个“有状态会话层”。Cookie 本质是客户端维护的状态标识，配合服务器端会话存储（如数据库或内存表），完成用户识别。

**易错点**：
- 误选 A（Web 缓存）：认为缓存能记录用户访问痕迹，但缓存是资源副本，与用户身份无关。
- 误选 D（持久连接）：持久连接只是 TCP 连接复用，HTTP 请求仍彼此独立，不能识别用户。
- 误选 C（条件 GET）：条件 GET 用于缓存验证，如 `If-Modified-Since`，与用户身份无关。
- 易混点：Cookie 与 Session 的关系。Cookie 是客户端保存标识的机制；Session 是服务器端保存用户状态的结构。题目问“识别用户”，核心是 Cookie 让服务器能区分不同客户端。

**命题规律**：考点属于 HTTP 协议基础，常考无状态性、Cookie、Session、缓存、持久连接的区别。变式可能：
- 给出具体场景，如“购物车功能依赖什么机制”。
- 问“HTTP 无状态如何解决”，答案常为 Cookie 或 Session。
- 结合 HTTPS、第三方 Cookie 等扩展考查安全与隐私。
复习时应重点记忆 Cookie 的工作流程（`Set-Cookie` / `Cookie` 首部），并区分它与缓存、持久连接、条件 GET。可类比算法竞赛中“记忆化搜索”：HTTP 本身无记忆，通过 Cookie 这个“备忘录”把状态挂在客户端，实现跨请求的状态传递。
